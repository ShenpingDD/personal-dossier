# 汲古 · 个人文档知识库

> **汲古**（Dossier）—— 售前解决方案经理 / 项目经理的个人文档知识库：一个客户一卷，问出来每句带出处。

*Jigu: a local-first personal document dossier for presales and project managers.*

写方案时最贵的三分钟，是「上次那个类似项目是怎么答的」——资料散在微信、邮箱和 D 盘十几个文件夹里，文件名还都叫「最终版 2」。
汲古解决的就是这件事：**把客户给的文件和我方出的方案，按「卷」收进来，随时能问，答案指得回原件。**

---

## 一、Personal 在这里是三条硬约束

不是三个形容词，是三条会把功能砍掉的限制：

| 约束 | 砍掉什么 | 为什么必须砍 |
|---|---|---|
| **文件不出本机** | 云同步、在线协作、多租户 | 售前的客户资料不能上第三方服务器，这条不可谈判 |
| **只服务一个人** | 账号体系、权限模型、审批流、冲突合并 | 一个人用的系统，90% 的企业级复杂度都是负债 |
| **五年后还能搬走** | 任何私有存储格式 | Markdown + SQLite + 原件目录，删掉本项目也不丢数据 |

如果这三条里有一条不成立，那你要找的不是这个项目。

## 二、它做什么

「一卷」= 一个客户或一个项目的全部上下文：客户给的需求、我方出的方案、报价、会议纪要、往来邮件附件。

```
收 → 解 → 存 → 问
```

| 层 | 做什么 | 不做 |
|---|---|---|
| **收** | 原件归档（不改名、不动目录）、按卷归属、去重、版本留痕 | 不做网盘、不做 OCR 云端排队 |
| **解** | Word / PPT / Excel / 扫描 PDF → Markdown，**表格保表头**，扫描件走本地 OCR | 不和「支持 100 种格式」较劲 |
| **存** | 分块 + 元数据（卷 / 文件 / 页 / 行 / 时间）+ 本地向量库 | 不发明新的存储格式 |
| **问** | 混合检索 → 精排 → 带出处的回答，点开回到原件那一段 | 不做聊天机器人扮演 |

**出处到什么粒度**——这是本项目最较真的一层：

- PDF：**页码 + bbox**（页面上那一块矩形，不是「大概在某页」）
- PPT：**第几页第几个形状**
- Word：**block 编号**（第几段，不是「在文档里」）
- Excel：**工作表 + 行号**，且表头必须回填到每一行

## 三、和多数「个人知识库」项目的区别

同类项目常见的样子是：Docker Compose 起五个容器，接一个通用文档加载器，chunk 完丢进向量库，回答里附一个「来源：某文件」。
能跑，但三件事会漏：

1. **中文表格进库就散架。** 通用加载器读 Excel 只读单元格，不知道哪一行是表头，合并单元格一展开就错位。本项目做表头回填，并且**把猜不准的标出来**——分三档：`header_trailing_empty`（合法，忽略）、`header_column_mismatch`（列数对不上，要查）、`header_row_suspect`（表头可疑，抽查）。
2. **出处只到文件级。** 「来源：报价单.xlsx」对售前没用，他要的是「第 12 行，单价那列」。所以本项目给每条 chunk 存 locator，并**逐条校验能不能真的定位回去**（这是可以量化的，见下）。
3. **没有验收。** 检索变差是无声的——换个解析器、加个字段，答案就悄悄烂了。本项目内置评估闸门：`recall@k`、`citation_recall`（答案里的引用是否真的支持那句话）、`refusal_accuracy`（该说「库里没有」时有没有瞎编）、`uncited_answers`（无出处断言数），`--fail-under` 直接当 CI gate 用。

## 四、它确实更重，我们认这个代价

同类项目强调「一条命令跑起来」。本项目选择了更重的一条路，代价写在明面上：

| 代价 | 具体是什么 | 换到什么 |
|---|---|---|
| **首次解析慢** | 一份 60 页扫描 PDF 要几分钟（本地 OCR + 版式分析） | 换到文字层准确率和可定位的 bbox |
| **依赖不轻** | 需要本机跑得动 OCR 与向量模型（Apple Silicon 上 16 GB 内存可用） | 换到全程离线，文件不出本机 |
| **格式覆盖窄** | 只认真做 Word / PPT / Excel / PDF 四类 + Markdown | 换到每一类都做到能定位回原件 |

**轻的是安装，重的是结果。** 如果你的场景是「一次入库、长期复用」，重的这部分只付一次；如果只是临时问几份文件，用轻的方案更合适——这不是缺点，是适用范围。

## 七、不做什么（Scope）

写在这里，是为了对「被要求支持一切」有据可拒：

- ❌ 不做协作、不做 SaaS、不做多租户
- ❌ 不做「支持所有格式」——四类之外按需加，不承诺
- ❌ 不训模型、不微调、不绑死某家 LLM（生成层可替换）
- ❌ 不发明检索算法，用成熟方案，把力气花在解析与验收上

## 九、关于名字

**汲古**，取自明末毛晋的藏书刻书楼「汲古阁」——「汲」是从井里打水，也是从旧卷里取用。

售前最贵的能力不是写新方案，是**知道上次怎么写、并取得出来**。名字说的是这个动作：你的旧方案都还在，等着被汲上来。
「卷宗」是它装东西的方式（英文 Dossier），「汲古」是它干的事。
